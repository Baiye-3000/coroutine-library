# 协程运行时重构 V2 规格说明

## 背景

现有项目是面向教学的 Linux 有栈协程实现，基于 `ucontext`、epoll、全局任务队列和互斥锁调度。源码按渐进式示例组织在 `fiber_lib/` 下；其中 `6hook` 是功能最完整的版本，但尚未提供统一构建、测试、基准测试或负载均衡实现。

本次重构将在保留旧示例的前提下，新建可维护、面向服务器运行时的协程库。范围包括全局调度锁竞争、固定线程配置、固定协程栈、不完整的阻塞调用拦截、线程亲和性不足、负载反馈缺失，以及性能结论不可复现等问题。

## 目标

- 提供 Linux C++17 协程运行时，具备统一的构建、测试、基准测试和文档入口，同时保留 `fiber_lib/` 作为旧版教学代码。
- 未配置时根据可用 CPU 核数选择工作线程，并允许显式配置覆盖。
- 使用可切换的轮询、最少负载、亲和性优先和自适应策略，为新任务及恢复任务选择工作线程。
- 使用每工作线程本地队列和工作窃取机制，使空闲工作线程能够取得可运行任务，而非依赖全局调度队列互斥锁。
- 在首选工作线程未过载时，保持可恢复协程的线程亲和性。
- 对启用 Hook 的协程代码，将支持的阻塞 I/O 和睡眠操作转为经事件循环等待，避免阻塞工作线程。
- 以默认 100 ms 的可配置采样周期，收集每工作线程的队列、完成量、等待时间和 CPU 负载。
- 建立可重复执行的基线与对比基准，测量吞吐量、尾延迟、上下文切换、Cache Miss、内存和负载均衡情况。
- 每个里程碑仅在规定测试通过后创建提交，并推送至 `https://github.com/Baiye-3000/coroutine-library`。

## 功能需求

- F1：新运行时必须通过一个已文档化的 CMake 入口构建，且不得要求修改 `fiber_lib/` 下文件。
- F2：未配置工作线程数时，运行时必须根据机器在线 CPU 数创建正数工作线程；调用者可显式设置正数线程数。
- F3：调度器必须使用每工作线程的并发可运行任务队列，正常分发路径不得使用单一的、由互斥锁保护的全局任务队列。
- F4：调度器必须支持轮询、最少负载、亲和性优先和自适应四种工作线程选择策略，并能通过运行时配置切换。
- F5：自适应选择必须依据队列深度、采样 CPU 使用率、队列等待时间和协程亲和性计算，并允许配置权重和过载阈值。
- F6：空闲工作线程必须依次检查本地队列和共享入口，然后尝试从其他工作线程窃取可运行任务，最后才阻塞等待；提交任务时必须唤醒符合条件的空闲工作线程。
- F7：因定时器或 I/O 就绪而让出的协程必须保留其上次运行的工作线程偏好。仅当首选工作线程不可用或超过配置的亲和性负载阈值时，才允许迁移。
- F8：启用协程执行时，必须为 `read`、`readv`、`recv`、`recvfrom`、`recvmsg`、`write`、`writev`、`send`、`sendto`、`sendmsg`、`connect`、`accept`、`poll`、`sleep`、`usleep` 和 `nanosleep` 提供非阻塞等待语义；未启用时必须保持底层系统调用行为。
- F9：支持的 Hook 操作必须安全处理就绪、超时、中断、关闭和取消，并向调用者返回标准错误结果。
- F10：运行时必须维护每工作线程的负载快照，至少包含队列深度、CPU 使用率、已完成任务数和队列等待时间；采集器必须以可配置周期发布快照，默认值为 100 ms。
- F11：运行时必须暴露调度器和负载均衡快照，供自动化测试和基准报告使用。
- F12：仓库必须提供确定性的单元测试和集成测试，覆盖各调度策略、工作窃取、亲和性回退、线程数选择、指标采集和每类支持的 Hook。
- F13：仓库必须提供基准测试工具和文档，记录命令、环境、原始结果及派生指标，包括上下文切换、QPS、P99 延迟、Cache Miss、协程容量/内存、CPU 使用率标准差和最大/最小工作线程负载比。
- F14：实现必须按 M0 至 M6 里程碑交付。每个里程碑必须先运行并通过文档中规定的测试集，随后才可创建提交并推送至指定仓库。

## 非功能需求

- N1：目标执行平台为 Ubuntu 22.04 或兼容的 Linux 发行版，要求支持 epoll、pthread、`ucontext` 和 C++17。Windows 不属于运行和性能验收平台。
- N2：运行时公共 API 和测试套件必须使用文档规定的工具链，在启用警告的条件下编译且无编译错误。
- N3：并发队列和调度器操作必须在仓库的压力测试及可用的 ThreadSanitizer 配置下无数据竞争、无死锁。
- N4：协程栈管理必须支持基准创建或复用至少 100,000 个协程实例，并根据所选栈策略和宿主环境记录内存上限及实际结果。
- N5：性能结论只能来自同一主机、相同命令下与 M0 基线数据的可重复对比。相关工作负载和工具可用时，目标为吞吐量提升至少 30%、P99 延迟降低至少 20%、上下文切换减少至少 30%、Cache Miss 减少至少 10%。
- N6：在已文档化的均衡负载基准下，工作线程 CPU 使用率标准差必须不高于 5%，最大/最小归一化工作线程负载比必须不高于 1.5；该条件适用于至少两个活跃工作线程且存在足够并行任务的场景。
- N7：所有公共配置默认值、基准测试假设、局限和测试命令必须以中文或英文记录在仓库文档中。
- N8：新增源码、测试和基准必须保持一致格式，且不得将生成的二进制文件或构建目录纳入版本控制。

## 非目标

- 重写或删除现有的 `fiber_lib/` 教学阶段代码。
- 在本次交付中支持 Windows、macOS、io_uring、kqueue 或其他非 Linux 事件后端。
- 以无栈语言/运行时模型替换基于 `ucontext` 的有栈协程；M6 仅实现动态栈或栈池原型。
- 对不同硬件、内核、编译器或外部压测工具保证固定的绝对性能数值。
- 在协程正在执行时迁移它，或从进程崩溃、永久卡住的操作系统线程中恢复。
- 构建生产级 HTTP 框架、协议解析器、监控 UI 或分布式负载均衡器。

## 验收标准

- AC1：全新 Ubuntu 22.04 兼容环境可通过唯一文档化的 CMake 流程构建新运行时和测试目标，且重构不会改动旧版 `fiber_lib/` 树。（F1、N1、N2）
- AC2：测试能够证明默认工作线程数来自 CPU 核数，且显式线程数配置可生效。（F2）
- AC3：并发调度压力测试完成时无死锁、无数据竞争报告；架构测试证明常规任务分发使用工作线程本地队列，而不是单个受互斥锁保护的全局任务队列。（F3、N3）
- AC4：测试可选择全部四种调度策略，并在受控负载快照下验证其目标工作线程符合预期。（F4、F5）
- AC5：集成测试能够制造负载不均，验证空闲工作线程窃取并完成排队任务，且验证新任务会唤醒符合条件的空闲工作线程。（F6）
- AC6：测试证明让出的协程在首选线程低于阈值时回到该线程，在该线程过载或不可用时回退到其他线程。（F7）
- AC7：Hook 集成测试覆盖 F8 的全部操作类别，验证非阻塞成功、超时/错误传递和未启用模式下的透传行为。（F8、F9）
- AC8：指标测试在配置采样周期下观测到至少两次采集器更新，并在任务完成后验证快照字段。（F10、F11）
- AC9：单元测试和集成测试目标覆盖 F2 至 F11 的全部需求，并在目标平台通过。（F12）
- AC10：M0 记录基线命令和原始结果；最终性能报告记录匹配的对比结果，并明确每项 N5 和 N6 指标为通过、未通过或因工具/环境不可用而无法测量，同时说明原因。（F13、N5、N6）
- AC11：栈管理基准创建或复用至少 100,000 个协程实例，并报告栈策略和实际内存结果。（N4）
- AC12：仓库历史中存在 M0、M1/M2、M3、M4、M5 和 M6 对应的里程碑提交；每项提交均在该阶段文档化检查通过后创建和推送，并记录验证证据。（F14）
